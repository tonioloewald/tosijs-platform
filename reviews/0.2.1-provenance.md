## Blockers (must fix before tagging 0.2.1)

### B1. #28 is only half-fixed: manifest `derive: {op:'principal'}` still names the role document's first uid
**correctness, confirmed.** The security lens reported the same thing independently (minor, unverified); merged here.

**Where:** `functions/src/install/compile.ts:335-337`. The derive context gets `{ uid: r?.userIds?.[0], name: r?.name, roleId: r?._id }` and never reads `r.principal`, although write-pipeline.ts:313 passes the full UserRoles in.

**What goes wrong:** a contact-matched human writes through a role document that lists a service principal first (the virta board shape that test 7b covers). `_by.uid` is the human, which is correct. A manifest-derived `author` or `owner` field is the service principal, and a derived `name` is the role document's name. One document then names two different authors, and any ownership rule keyed on the derived field credits the wrong person. After this fix, this is the only identity read of `userIds[0]` left. The other two, in provenanceOf and auth/endpoint.ts:78, are only fallbacks.

**Fix:** use `uid: r?.principal?.uid ?? r?.userIds?.[0]` and `name: r?.principal?.name ?? r?.name`, and add `principal?` to the local cast. Better still, extract one `principalIdentity(userRoles)` helper that provenanceOf, the derive context and /token all call. Add a compile.test case where `principal.uid !== userIds[0]`. The existing tests at compile.test.ts:327/362 pass no `principal` and cannot catch this.

**Re-review scope:** correctness and blast-radius, over the remediation diff only.

### B2. `_by.name` now comes from the caller's credential, falls back to the email address, and is published on publicly readable docs
**correctness major (confirmed), merged with security minor (confirmed).**

**Where:**
- `functions/src/collections/join-roles.ts:106` (`credentialName`), which returns `name`, else `email`, with no `email_verified` check.
- `utilities.ts:~444`: `getUserRoles` sets `principal.name` for **every** signed-in writer.
- `write-pipeline.ts:156-160`: provenanceOf now prefers `principal.name`.
- `auth/endpoint.ts:~134` and `authorize-endpoint.ts:~180`: the name is captured at /token mint and at /authorize approval.

**What goes wrong:**
1. **PII leak.** A writer whose token has no `name` claim (email/password, email-link, or a provider account with no display name) gets their raw email address in `_by.name`. `doc.ts` GET with `access === ALL` returns `{...data, _path}` without stripping `_by`, and posts are `public: { read: ALL }`. So every post that writer authors publishes their email address. In 0.2.0 this was the curated role document name, apart from the one claim.ts configurator path.
2. **Spoofable attribution.** The `name` claim is the user's own displayName, which they can set with `updateProfile`. The email may be unverified. Either way, any role-holder can have their writes, and every token they mint from then on, attributed to "Tonio Loewald". `_by.uid` and authorization are unaffected. The attribution string is exactly the field virta displays for #28. The unverified-email fallback also contradicts `lookupEmail`, the function just above it, which treats an email as authoritative only when `email_verified === true`.
3. **Inconsistent naming by credential.** Pre-0.2.1 tokens and pre-deploy /authorize approvals fall back to the role document name, while ID-token writes use the credential name.

**Fix (decision needed from Tonio; do not guess):**
- Minimum: never fall back to email. At the least, require `email_verified === true`, and preferably fall back to the role document `name` instead of any address.
- Then pick one of these and write it down:
  - (a) Keep `_by.name` operator-sourced: the role document `name` when the principal's uid is actually on that document, with the credential name only for contact or shared matches. Record the self-asserted name separately, e.g. `_by.displayName`.
  - (b) Document in roles.ts, write-pipeline.ts and the 0.2.1 CHANGELOG that `_by.name` is self-asserted and display-only, and that `_by.uid` is the identity.
- Tests: `_by.name` for a normal, non-contact human writer; a writer with no display name (must not be an email); an unverified email.

**Re-review scope:** correctness and security, over the remediation diff.

## Follow-ups (non-blocking; file them, do not drop them)

### -> this repo's `TODO.md` (correctness / security / efficiency / blast-radius / coverage)

**Correctness / coverage**
- [ ] **(unverified) `scripts/verify-sequence.js:41` noop check is a tautology** (`cond ? rows===0 : rows===0`). Assert `same.status === 200` and `/unchanged/` in the body. As written, a wrong 409 on an identical re-PUT to an immutable collection would pass, so earlier greens from this check don't prove noop semantics.
- [ ] **(unverified) Seq-only mutable collections have no behaviour test through the new transactional /doc branch.** The only live `seq` collection was switched to `immutable:true`. Cover: an update gets a fresh `_seq`; PATCH merges; POST on an existing doc gives 403 `exists`; afterWrite runs through `commitTransactionally`. Either add a second non-immutable seq collection to the live script, or add a commit.ts unit test with a fake transaction.
- [ ] **(completeness gap) Sub-collection paths on the transactional branch.** `FirestoreStore.resolve` rebuilds `a/1/b/2` as `a/b/2`, so commit.ts's `admin.firestore().doc()` gets an odd-segment path and returns 500, and `collectionPath()` looks up the wrong config. This was already broken, but it is now reached for any immutable or seq sub-collection. Add a test, then fix it or refuse such paths explicitly.
- [ ] **(completeness gap) Transaction semantics on /doc.** Validate and derive hooks may now run more than once on transaction retry, and derive's `shortId` and `now` are non-deterministic across retries. A hook that throws is now a caught 500 `internal`. ABORTED after contention returns 500 (should it be 409/503?). Decide on and pin these behaviours. Only the 5-way same-id race was exercised live. PATCH merge, the `unchanged` reply, `field=value` creates and the 409 immutable reply were checked by reading the code only.
- [ ] **(completeness gap) Uniqueness equivalence.** commit.ts `isUnique` (`tx.get(where(field,'==',value).limit(2))` on the physical parent path) has not been checked for equivalence with `store.isUnique` / `primitives.isUnique`: null or undefined values, and path scoping for namespaced collections. Add characterisation tests that run both.
- [ ] **(completeness gap) Legacy credentials.** No test covers a token minted before 0.2.1 (no `principalName`), or an /authorize request approved before the deploy and exchanged after it (no `approvedByName`). Code reading says both fall back to the role document name; pin that with tests.

**Security**
- [ ] **(unverified) /token cross-principal scoping has only a regex test.** The `principal?.uid` change in `functions/src/auth/endpoint.ts:77` closes a real 0.2.0 hole: B's agent token could list and revoke A's tokens when they share a role document that lists A first. It is covered only by `endpoint-wiring.test.ts`, which greps utilities.ts, not endpoint.ts. Add a behavioural emulator check: two uids on one role document with A first, B's token calls GET /token (expect B's tokens only) and DELETE /token?id=<A's> (expect 404). Also add a structural assertion on endpoint.ts.

**Blast-radius / docs**
- [ ] **(unverified) npm consumers get the #28 fix only if they set `UserRoles.principal`.** Without it, provenanceOf quietly falls back to `userIds[0]`, and the package exports no helper (`credentialName` is host-only). In the 0.2.1 CHANGELOG, add an "Upgrading the npm package" note:
  - set `principal = { uid, name }` from the verified credential;
  - for immutable or seq collections, read `exists` and uniqueness inside the host's commit transaction (#1184; commit.ts, where that lesson lives, doesn't ship).

  Also point to this from the `principal` doc comment or the lib/index.ts scope doc. Consider exporting a `principalIdentity` helper (see B1).
- [ ] **(confirmed, existing, not in this diff) `package.json:28` `kill-ports`** runs `lsof -ti:<ports> | xargs kill -9` without `-sTCP:LISTEN`. It SIGKILLs connected clients (browser network processes, test runners) and unrelated listeners on 8080 and similar ports, and hides the result with `2>/dev/null || true`. Fix: use `lsof -ti tcp:... -sTCP:LISTEN`, check the pid's command (`ps -p PID -o comm=`), send SIGTERM before SIGKILL, and print what was killed to stderr.

**Efficiency**
- [ ] **(unverified) No size reporting at build or package time.** Measured: dist-lib 68,795 → 70,504 B (+1,709 B; +454 B JS, in roles.d.ts and write-pipeline.js for `principal`). Published 0.2.0 unpackedSize is 79,430. The growth is justified by #28. Have `verify-package.js` or preflight print packed and unpacked size and the delta against `npm view service-compris dist.unpackedSize`. Note the ~1.7 KB growth in the 0.2.1 CHANGELOG.
- [ ] **(unverified, nit) Double read on the immutable/seq write path.** In `functions/src/doc.ts:398`, the outer `store.get(canonicalPath)` result is discarded when commitTransactionally does its own `tx.get`, costing one extra billed read and round trip per write. Optionally move the outer read into the GET/DELETE and non-transactional arms. Otherwise accept it.
