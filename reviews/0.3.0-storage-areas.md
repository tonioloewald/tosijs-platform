## Blockers

### B1. A comma-joined Content-Type gets past the allowlist and the sandbox, giving stored XSS on the site origin (security, confirmed)
Files: `functions/src/collections/blob.ts:128-129,236-240`, `functions/src/blob-handler.ts:83`, `functions/src/blob-endpoint.ts:107-110`.
- `bareType()` only splits on `;`, so `image/png, text/html` passes `contentTypeAllowed` through `startsWith('image/')`. It is then stored verbatim as `meta.contentType`.
- `SCRIPTABLE` is anchored with `^`, so `deliveryHeaders()` returns only `nosniff` and no sandbox CSP. `image/png, image/svg+xml` gets past the SVG sandbox the same way.
- On the streaming fallback, the endpoint sends that Content-Type unchanged from the site's own origin (`/blob/**` rewrite). Streaming is the default until a deploy grants "Service Account Token Creator". Under the Fetch spec's MIME extraction the last type wins, so the browser treats the body as HTML. The site CSP allows `'unsafe-inline'`.
- Impact: an `author` (write on `blog:public`) can store script that runs as the site and read an owner's ID token, which escalates author to owner. The server side was reproduced with `bun test` against the real `manifests/blog.json`. The browser step follows from the spec and was not run in a browser.
- **Fix (fail closed):** in `decidePut`, require the bare type to be exactly one RFC 7231 `token/token` (no commas, spaces or extra slashes). On the stream path, always send `Content-Security-Policy: sandbox; default-src 'none'`, and consider `Content-Disposition: attachment` for anything that is not inline media. Treat `+xml` suffixes as scriptable. Add tests with hostile input: comma-joined types, `+xml`, and whitespace or parameter tricks, through both `decidePut` and `deliveryHeaders`.
- Re-review scope: security + correctness over the remediation diff.

### B2. `storage.rules` still lets anyone read everything, so `blog:private` files can be listed and downloaded without going through `/blob` (security, found at triage by reading the code; not live-tested and not verified by a skeptic)
Files: `storage.rules` (catch-all `match /{allPaths=**} { allow read: if true; }`), `functions/src/blob-handler.ts:42-43`, `functions/src/blob-endpoint.ts:23`.
- `/blob` writes to the default bucket at `${area}/${path}@${sha16}`, for example `blog:private/...`. No specific rule matches a colon-prefixed key, so the catch-all applies. Under `rules_version = '2'`, `read` covers both `get` and `list`.
- So private-area objects can be listed and downloaded by anonymous callers through the Firebase Storage SDK/REST API, which bypasses `decideRead`. The content hash in the key gives no protection when the bucket can be listed.
- This file is outside the diff, which is why no lens looked at it. It is a blocker because 0.3.0 is the release that starts putting private bytes in that bucket.
- **Fix, shipping with 0.3.0:** make the storage rules deny by default, or at least deny every `/{area}` prefix that contains `:`, since the Admin SDK in `/blob` bypasses rules anyway. Add an upgrade note to CHANGELOG.md (around lines 48-51) telling consumers to deploy the new `storage.rules`. Record one live check (an anonymous list/get on `blog:private/` returns 403) in the review log.

### Majors to fix in the same remediation (confirmed; treat as gating)
- **M1. The PUT rollback deletes a live object at the same content address** (correctness, confirmed; `functions/src/blob-handler.ts:~198-205`). Two cases trigger it: the same bytes re-PUT with a new Content-Type, or two concurrent PUTs of the same bytes. Either way `objects.put` overwrites the live key K. If the commit then fails or is refused, the rollback runs `objects.delete(K)`, leaving metadata with no object behind it. This breaks the header invariant and was reproduced with the fakes. **Fix:** skip the rollback delete when `previous?.sha256 === d.meta.sha256`. Better, re-read the metadata and delete only if nothing references this sha. Add a test: same bytes, new type, commit refuses or throws, old object survives.
- **M2. A cached public 302 points at an object that a replace or move has already deleted** (correctness, confirmed; `blob-handler.ts:161-166,209-211,285`). A redirect with `public, max-age=3000` to the hash-specific key can be cached by the Hosting CDN and by browsers. The old object is deleted as soon as the commit succeeds, so replacing `cover.webp` breaks embedded images (NoSuchKey) for up to about 50 minutes. `scripts/verify-blob.js` calls `cloudfunctions.net` directly and bypasses the CDN, so its green "readers get the new bytes" result does not cover this case. **Fix:** either delay deletion of replaced public objects past max-age plus the signing TTL, or make the redirect `no-cache` or a short `s-maxage`. Add a CDN caveat, or a check routed through Hosting, to `verify-blob.js`.
- **M3. `move` never checks read access on the source, and PUT's `unchanged` reply confirms a file's contents** (security, confirmed; `functions/src/collections/blob.ts:306-321`, `blob-handler.ts:185-189,239-298`). `decideMove = decideDelete(from) + decidePut(to)`, and `DELETE` maps to `write`. A write-only role on a drop-box area can move a file it cannot read into an area it can read. PUT's `{status:'unchanged'}` tells a writer without read access that a guessed body matches the stored file. This does not affect today's blog manifest, but it is exported, consumer-facing API. **Fix:** require `decideRead(from, srcMeta)` in move and fold a refusal into the opaque 404. Answer `unchanged` as an ordinary success to callers without read access. Add a test that a write-only role cannot move a file out of an area it cannot read.

**To clear the BLOCK:** fix B1, B2 and M1-M3 with tests, deploy the storage rules to the sandbox, and record one live `verify-blob.js` run plus the anonymous-storage check. Then re-review with security + correctness scoped to the remediation diff.

## Completeness gaps (major release)

- **No evidence that `/blob` was exercised live.** `scripts/verify-blob.js` exists, but no AAR, review or provenance record shows it being run. Still unverified: signed-URL redirect versus the streaming fallback (the signBlob role; B1 applies whenever streaming is used); a 25 MB PUT under 256 MiB memory and the 32 MB v2 request cap; and whether the `blob` function can be invoked publicly (CHANGELOG around line 51).
- **Two storage systems now coexist.** The legacy `storage.rules` write paths (`/blog/**` for any content role, `/users/{uid}/**`) still accept direct client uploads that skip `/blob` metadata and the maxBytes/contentTypes limits. Decide whether both stay (this overlaps B2).
- **Hosting path.** Verify that the `/blob/**` rewrite passes the raw PUT body and Content-Type intact through Hosting. Verify that the site CSP (`img-src`/`media-src`) allows the 302 target (`storage.googleapis.com`) for embedded media.
- **Node 20 -> 22 runtime bump** (`1988a01`): not checked against the functions `package-lock` (firebase-functions/admin versions), the CI node version, or the emulator note in CLAUDE.md. It changes the runtime of every deployed function.
- **Orphan cleanup.** Replace and move delete the old object with `.catch(() => undefined)`, so a partial failure leaves orphaned bytes silently, and nothing reconciles or garbage-collects them. The design accepts this cost, but it should be tracked as a follow-up task.
- **Published tarball.** Run a `build:lib` pack dry run to confirm `collections/blob.js` ships in `service-compris` and pulls in no firebase import. By inspection it imports only `access.js` and `roles.js`.
- **SSR race fix blast radius.** The only evidence that no other `onPrefetch` handler used the removed `currentPage` export is a grep. The `x-forwarded-host` trust question is covered by the plausible minor above.
