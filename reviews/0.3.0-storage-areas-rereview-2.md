## Blockers

### B1: `/stored` serves private storage-area objects and acts as an anonymous content oracle

**Status:** confirmed by correctness, security and blast-radius. Anchor: `functions/src/stored.ts:55-71`.

**What the code does**
- `stored.ts` takes the object path from `req.url` or the client-supplied `x-forwarded-url` header.
- The path regex `(.+)` accepts `:` and `@`. The only checks are for `..` and a leading `/`.
- There is no `getUserRoles`, no namespace refusal and no `decideRead`.
- It then calls `admin.storage().bucket(`${projectId}.appspot.com`).file(path)`. The Admin SDK ignores `storage.rules`, so the new `!first.matches('.*:.*')` exclusion never applies here.
- `/blob` writes to `admin.storage().bucket()`, the default bucket, under the key `<ns>:<area>/<path>@<sha256[0:16]>` (built in `blob-handler.ts` `objectKey`).
- On production (`liquid-force-425209-g2`, an appspot-era project), `src/firebase-config.ts:17` sets the bucket to `${PROJECT_ID}.appspot.com`, so `/stored` and `/blob` almost certainly share a bucket.

**Attacks**
- **(a) Access that never expires.** Anyone who has seen a private signed `/blob` URL knows the object key from it, for example a reader who was later revoked, or a URL that leaked through logs or a Referer header. That person can fetch `/stored/<key>` anonymously forever. Each request returns a fresh signed redirect with `Cache-Control: public, max-age=3300`, which defeats both the private TTL and no-store.
- **(b) Content oracle.** An anonymous caller hashes a guessed body and requests `GET /stored/<ns>:<area>/<path>@<sha16>`. A 302 or 200 means the guess matches the stored file; a 404 means it does not. This is the M3/G1 oracle, now available with **no role at all**. It is practical for low-entropy content such as votes, yes/no values or short codes.

**Why the evidence missed it**
- verify-blob check 14 probes only direct GCS, never `/stored`.
- On the sandbox the bucket is `.firebasestorage.app`, so `/stored` looks in the wrong bucket and the run looks green.
- The re-review's filed follow-up is to "fix" that bucket mismatch. Doing so *opens* the hole on the sandbox too.

**Caveat:** that production's default bucket is `.appspot.com` is inferred from the client config and the project's age. It has not been probed live. The class is open on any deployment where it is true.

**To clear the block**
1. In `stored.ts`, refuse any path whose first segment contains `:` (raw **and** percent-decoded) with the same 404 as a missing file, before calling `exists()`.
   - Better: export a single `isAreaKey()` from `blob-handler.ts`, which stored.ts already imports from, and mirror it in storage.rules so the predicate has one owner.
   - Or: switch to an explicit allowlist of legacy prefixes (`blog/`, `public/`, `users/`).
2. Add a unit test: a namespaced path to /stored returns 404.
3. Add a verify-blob probe: `/stored/<privateKey>` returns 404. It must run against a project where /stored and /blob share a bucket.
4. Fix the hardcoded `appspot.com` vs default-bucket mismatch in the same change, and record which bucket production `/blob` writes to.
5. Per the STOP line, first write down the list of every reader and writer of the bucket (`/blob`, `/stored`, direct GCS via storage.rules, and the legacy `/blog/**` and `/users/**` uploads). Show G1 and G2 against each one, rather than patching `/stored` on its own.

**Re-review scope:** correctness + security over `stored.ts`, `verify-blob.js` and the bucket-resolution change, plus the recorded live evidence.

## Follow-ups (non-blocking)

### → this repo's `TODO.md` (correctness / security / coverage lenses)

- [ ] **(confirmed, minor, correctness+security) G1 timing side-channel on the mutable-area `reuse` path.** Anchor: `functions/src/blob-handler.ts:258-290`.
  - For a non-reader, the `reuse` flag (`previous?.sha256 === d.meta.sha256`) skips `objects.put` (up to 25 MB) and the old-object delete. The response bodies are identical, but the latency reveals whether a guess matched. This contradicts the rule stated in the code comment.
  - The probe works once (a miss overwrites the file), and it needs write access to a write-only mutable area. Immutable areas are unaffected.
  - Fix: when `!canRead`, do not branch on `reuse`. Always put (the key is content-addressed, so rewriting the same bytes is idempotent) and defer or fire-and-forget the old-object delete. Alternatively, record timing as an accepted residual in the rule comment and the CHANGELOG, and stop claiming the class is closed.
  - (The security lens filed the same finding as an unverified nit; it is merged here.)
- [ ] **(unverified, minor, correctness) The reuse path can commit metadata that points at a deleted object.** Anchor: `functions/src/blob-handler.ts:258`.
  - Race: a non-reader's identical re-PUT reads `previous` (sha A) and skips the put. A concurrent replace then commits B and deletes object A. Finally the first request's upsert commits sha A with no precondition, so the metadata points at a missing object.
  - This is new for non-readers in this diff.
  - Fix: make `commitMeta` conditional on the sha that was read. Re-putting on reuse (the timing fix above) also closes it. Add a fake-store test that interleaves a replace between `getMeta` and `commitMeta`.
- [ ] **(unverified, minor, correctness/coverage) The delivery-mode-specific changes have no test that fails without them.** Anchor: `functions/src/blob-endpoint.ts:56`.
  - Reverting either change keeps every test green: `responseType: meta.contentType` on `getSignedUrl`, and the `deliveryHeaders` in `stored.ts`'s stream fallback.
  - Add a stubbed-bucket endpoint test for `stored.ts` streaming (assert CSP + `nosniff` for `image/svg+xml`), and assert that `getSignedUrl` receives `responseType`.
  - Record in the review log that type forcing on the redirect path has **not** been verified live, because the sandbox cannot sign. Also check whether V4 signed URLs honor `response-content-type`.
  - Note that `stored.ts`'s signed-redirect branch passes no `responseType`, so after a type-only re-PUT it would serve the stale object type.
- [ ] **(unverified, minor, security) G2's "a first-segment test is enough" argument has no probe behind it.** Anchor: `scripts/verify-blob.js:160`.
  - The argument rests on the claim that the Storage API rejects a non-empty list prefix that does not end in `/`. Nothing probes that.
