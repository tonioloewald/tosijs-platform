## Release-blocking items (fix all four in one pass)

### B1. Browser-approved upgrade that adds capabilities is reported as installed but is only parked (correctness, major, verified)
`functions/src/install/endpoint.ts:373`

- The first `runInstall` returns needs-approval with `added: CapabilityEntry[]`, an array of `{name, capability}` (`apply.ts:81`).
- The retry passes that array, cast to `Record<string, CapabilityDeclaration>`, as `approving`. `decideInstall` looks up `approving[name]` (`apply.ts:304-309`), which is undefined on an array, so the second run is needs-approval again.
- That result carries no `error`, so `decided({ body })` records status `installed` (`proposal.ts:109-112`). The page gets a 200, and the CLI prints `→ installed` and exits 0.
- The grant stays `pending` on the old version and capabilities. It is fail-closed (nothing is granted without approval), but the path cannot complete and says it did.
- Same root cause on the page: `proposal-page.ts:136` uses `Object.keys(b.added)`, which prints `0, 1` instead of capability names.
- Each parked run also commits an install-log entry, the second with `approvedCapabilities` stored as an array.
- Not affected: new installs, and upgrades that add no capability.
- Established by reading code and types, not by running the flow. No test covers approve with added capabilities.

Fix:
- Build the record with `Object.fromEntries(added.map(({name, capability}) => [name, capability]))`.
- Treat a second needs-approval as `decided({failure})`, never `installed`.
- Map `b.added` to `.name` on the page.
- Add a test that drives approve on an upgrade adding a capability and asserts the grant becomes active.

### B2. The pages that grant authority can be framed by any site (security, major, verified)
`functions/src/page-csp.ts:15`, and the `/@(authorize|claim|install)` header rule in `firebase.json`

- `PAGE_CSP` has no `frame-ancestors`, and `default-src` does not fall back to it. Nothing sets `X-Frame-Options`. Neither page script has a frame-bust.
- This release adds the Hosting rewrites that make `/install`, `/authorize` and `/claim` work on the site domain for the first time.
- `action=propose` and `/authorize` `action=start` need no credentials. The only defence against approving a request you did not start is on-page text (the confirmation code), which a framing page can cover.
- Outcome if exploited: a configurator-level install of an attacker's manifest, or a scoped agent token carrying the victim's roles.
- Not tested: that Firebase popup sign-in completes inside a cross-site frame. The Google account popup stays visible, which lowers likelihood but does not remove the attack.

Fix:
- Add `frame-ancestors 'none'` to `PAGE_CSP` and to the `firebase.json` rule together. Hosting replaces the function's header, and `scripts/storage-rules.test.ts` pins the two equal.
- Add `X-Frame-Options: DENY` to the Hosting rule.
- Add a test asserting `PAGE_CSP` contains `frame-ancestors 'none'`.

### B3. Unauthenticated `POST /install?action=propose` writes up to 200 KB per call and nothing ever deletes it (security, major, verified)
`functions/src/install/endpoint.ts:308`, `functions/src/install/proposal.ts`

- `propose` runs before any role check and creates a document in `system:install-proposal` up to `MAX_PROPOSAL_BYTES` (200 KB).
- Expiry is derived on read only. No code path, TTL policy or script deletes these documents, and there is no cap on pending proposals.
- `expiresAt` is stored as an ISO string, so a Firestore TTL policy could not use it as written.
- The only limiter is in-memory per instance at 100 requests/min, keyed on the leftmost `X-Forwarded-For` entry (`utilities.ts:111-121`). One IP can still write 20 MB/min per instance indefinitely, billed to the host owner.
- Not tested against this deployment: that the leftmost entry is client-chosen (Google documents appending, the code comment says overwriting). The finding stands without it.
- Integrity and confidentiality are not affected; proposals are inert until approved.

Fix:
- Delete proposals when decided or expired: a TTL policy on a real timestamp field, or a sweep of expired documents on each propose.
- Cap the number of live pending proposals per host.
- Lower the size cap to what real manifests need.
- Separately, key the limiter on the entry Google appended and correct the comment.

## Follow-ups by destination

### This repo: fix now or file to `TODO.md`

**Verified minors**

- [ ] **T1 (security)** `functions/src/blob-handler.ts:441`: blob `import` checks size and hash, then copies with no generation precondition. A caller with area write can swap a `users/<uid>/...` source between head/hash and copy, bypassing `maxBytes` and the 25 MB ceiling and leaving metadata that misdescribes the bytes. Pin the source generation across head, hash and copy, or verify the destination after the copy. Add a test where the source changes mid-import.
- [ ] **T2 (efficiency)** `functions/src/commit.ts:186`: render-store invalidation runs once per committed row, serially and awaited. Estimated 6 to 9 round trips per post row against 1 at v0.3.0. Batches are capped at 100 writes, so the claimed timeout at "a few hundred rows" cannot happen; a 100-row batch may approach the default 60s. Not measured live. Union and dedupe deps per commit and call `invalidateDependents` once.
- [ ] **T3 (efficiency)** `functions/src/render/hooks.ts:19`: invalidation hooks are installed unconditionally. A host with `RENDER_ON_STORE` unset pays one batch write of 2 to 6 documents plus one empty query on every post/page/config save. `system:render-log` has no cleanup, though its growth is bounded. Either gate on the flag, or record always-on invalidation and its cost in DECISIONS.md D23. Per the surface-don't-apply rule, the DECISIONS edit is the owner's call.
- [ ] **T4 (blast radius)** `scripts/deploy.js:81`: `bun run deploy` passes `--force` to both firebase deploys, so remote indexes and functions absent from the checkout are deleted with no prompt or preview. `--dry-run` does not show deletions. Production has no drift today (exactly the three indexes in `firestore.indexes.json`). Drop `--force` from the firestore step, or list remote extras and require an explicit flag. Document it in the script header and BETA.md.
- [ ] **T5 (blast radius)** `scripts/backup-lib.js:30`: the nightly off-site archive is now default-allow. Anything outside the three-entry `LOCAL_ONLY` list goes unencrypted to iCloud and Google Drive, and the log names only what was excluded. No email addresses were found in the 2026-10-06 snapshot. The risk is the next private storage area or personal-data collection. Decide the off-site default (allowlist, or log every shipped collection and flag first-seen ones) and pin the off-site set in `backup-lib.test.ts`.
- [ ] **T6 (blast radius, pre-existing, not a regression)** `package.json:28`: `kill-ports` runs `lsof -ti:<ports> | xargs kill -9`, which matches connected clients as well as listeners. Reproduced harmlessly on a spare port. Add `-sTCP:LISTEN`, check the process identity, send SIGTERM first, and print what was killed.
