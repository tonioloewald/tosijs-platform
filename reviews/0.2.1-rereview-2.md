## Follow-ups

### `TODO.md` (this repo)

- [ ] **(minor, correctness, unverified; code sanity-checked) claim.ts fallback role-doc name `'Host owner'` is a constant in a `unique: ['name']` collection.** `functions/src/claim.ts:190`: `name: credentialName(user) ?? 'Host owner'`. The name is written with `tx.set`, which bypasses the uniqueness gate.
  - A second claimer on the claim-again path, with no display name and no uid-matched role doc (for example an email/password account), gets a second doc named "Host owner".
  - The same happens when a claimer's display name collides with an existing contact-matched doc's name, because `existingRoles` matches only on `userIds`.
  - After that, every non-no-op owner PUT/PATCH to either doc fails with `"name" is required to exist and be unique` until someone renames one.
  - This is a regression: the old `email ?? uid` was unique per user.
  - Separately, "curated when owned" then attributes every post by that owner publicly to "Host owner".
  - *Fix:* make the fallback unique and non-PII, e.g. `` `Host owner ${user.uid.slice(0, 8)}` `` (the uid is already public in `_by.uid`). Or omit the name so that `principalIdentity` drops `'unknown'` and the credential name wins. If a display name is used, pre-check uniqueness inside the claim transaction.
  - Add a second-claimer test.
  - *Cheap enough to fix before tagging if convenient. Otherwise schedule it for 0.2.2.*
- [ ] **(minor, correctness + blast-radius, unverified) Data that already carries an email has no remediation path.**
  - (a) `CHANGELOG.md:25` says role docs and tokens are "covered without a migration". But documents stamped under ≤0.2.0 still carry `_by.name = <email>` and are still served publicly by `/doc`, `/docs`, `/cachedQuery` and SSR. The read-time filter covers only future writes. Add an **"Action required"** note: pre-0.2.1 documents may carry an email in `_by.name` and need re-stamping or scrubbing. The 0.2.1 re-review's fix list, item 4, asked for this and it was not done.
  - (b) Add a `scripts/audit-host.js` check that flags:
    - public documents whose `_by.name` contains `@`;
    - role docs whose `name` contains `@` or equals one of their own contact values;
    - token records whose `principalName` does either.

    Without this, operators of sandbox, virta and loewald.com have no way to find the email-named role docs the CHANGELOG tells them to rename.
- [ ] **(minor, correctness + blast-radius, unverified) Document the `_by.name` filter heuristic as it is actually enforced.**
  - `functions/src/collections/roles.ts:~120–123` omits any name that contains `@` or that equals one of the principal's contact values (case-insensitive).
  - This fails closed, which is the right direction for a public-provenance field: attribution is lost, nothing is exposed. Keep the behavior.
  - The problem is that consumers get no signal. For example, a tosijs-virta operator who curated "Team @ Acme" or "ops@night-shift" silently gets no name in `_by` and in `derive:principal`.
  - State the rule in:
    - the CHANGELOG 0.2.1 entry (currently just "never an email address");
    - the `principalIdentity` doc comment;
    - the role-doc docs.
  - Add it to the existing virta-notification follow-up in `reviews/0.2.1-rereview.md`.
- [ ] **(nit, correctness, unverified) Contact-equality check matches only exact strings, ignoring case.** `functions/src/collections/roles.ts:120` uses `contacts.has(n.toLowerCase())`. A name that is a differently formatted form of a phone or address contact is still published (e.g. `'+15551234567'` vs `'+1 555 123 4567'`, or a value with surrounding whitespace). Emails are unaffected because the `@` rule catches them. *Optional:* trim both sides, and strip whitespace and punctuation for `phone` contacts. Low priority, because role-doc names come from operators or credentials in practice.
