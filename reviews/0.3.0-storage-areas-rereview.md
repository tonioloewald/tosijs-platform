## Gating items (must clear before tagging)

### G1. The M3 fix is incomplete: in an immutable area, a write-only caller can still confirm a guessed body (security, **confirmed**; correctness reported the same thing as an unverified minor, merged here)
File: `functions/src/blob-handler.ts:228-240`.
- The `unchanged` shortcut, which answers `replaced` to callers without read access, runs **before** `if (previous && config?.immutable) -> 409`.
- Take an `immutable: true` area where a role can write but not read, such as an append-only drop box.
  - A PUT whose guess matches the stored file gets **200 `{status:'replaced'}`**.
  - A PUT whose guess does not match gets **409 `immutable`**.
  - The two answers differ, which is exactly the oracle M3 was meant to remove.
- The 200 `replaced` answer is also false. Nothing is written, `_by`, provenance and timestamps are not updated, and the area cannot be replaced at all.
- The new M3 test only uses the mutable `blog:public` area. `log:frozen` grants authors read, so no test combines immutable with write-only.
- No deployed area is affected today, but this is exported, consumer-facing API. That was the same reasoning M3 was gated on.
- **Fix:** when the caller cannot read (`canRead` false), run the immutable 409 check before the shortcut, so a match and a miss answer the same way. A caller who can read may still get `unchanged`. Add a fake test: an immutable area with write but no read, where a matching PUT and a mismatched PUT return an identical status and body. Decide on purpose whether a no-op in a mutable area should keep reporting `replaced` without touching provenance, and document the choice.

### G2. The B2 fix has no test that fails without it, and the required live evidence is not in the review log (correctness, **confirmed**)
Files: `storage.rules:48`, `scripts/verify-blob.js`.
- Nothing in `bun test` evaluates `storage.rules`, and there is no emulator rules test. Reverting the rules would keep the suite green.
- The only live evidence is in the `bae8204` commit message: "old rules 200/200, new 403/403", "verify-blob 22/22". No `reviews/` or AAR entry records it, which the clearing condition required. The run also does not say which delivery path it exercised: signed redirect or stream.
- The new probe does one list at `prefix=blobtest:private/` and one GET of the exact key. It does not try:
  - an **empty-prefix recursive root list**, which returns 200 today (see the refuted finding);
  - a `delimiter=/` root listing, which might expose area names as prefixes.
- **Fix:**
  - Extend `verify-blob.js` so that, while a private object exists, it probes `?prefix=` with no delimiter and `?prefix=&delimiter=/`, and asserts that no `<ns>:<area>` key or prefix comes back.
  - Label each check with the path it exercises.
  - Run it against the sandbox and record the output in `reviews/0.3.0-storage-areas.md`, or in a re-review file, including the delivery path.
  - Ideally, add a `@firebase/rules-unit-testing` emulator test so that removing the rule fails.
- Re-review scope: correctness + security over `storage.rules`, `verify-blob.js` and the PUT ordering in `blob-handler.ts` only.

## Remediation evidence (2026-09-30)

**Loop flag answered.** Underlying problem: the PUT path was a chain of order-dependent early returns, so an inserted shortcut skipped a later refusal. Class fix: PUT is now built around one stated rule. A caller who cannot read gets a response independent of the stored content: never `unchanged`, and in an immutable area the same 409 whether or not the bytes match. It is tested as a property over two area shapes (immutable write-only, mutable write-only), and that test fails against the previous ordering (mutation-checked). B2 class: rules only grant, and the root list is recursive. So top-level objects are `get`-only and the root cannot be listed. `scripts/storage-rules.test.ts` fails on both the original rules and the first fix.

**B1 twin closed:** `stored.ts` streams with the same `deliveryHeaders` (nosniff, sandbox unless inert media). Not live-testable on the sandbox, because `stored.ts` hardcodes `<project>.appspot.com` and the sandbox bucket is `.firebasestorage.app` (a pre-existing bug, filed as a follow-up).
