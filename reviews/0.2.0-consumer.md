### B2. The 0.2.0 CHANGELOG entry is a draft written for the wrong audience (dx blocker; merges the docs major "no upgrade path", the dx minor "kernel API changes not named", and the plausible docs minor "security versions")
File: `CHANGELOG.md:3`.
- **Wrong audience.** The entry is headed "(draft)" and calls itself "the first beta on npm since 0.2.0-beta.2". But `npm view` shows latest=0.1.0, so the people who get `latest` are coming from 0.1.0. Their change set is beta.1 through beta.5.
- **Wrong content.** The entry lists host behaviour (the seq guard, the verified-email fix, the reserved namespace, no-store) and repo operations (OIDC, the virta board, the production registry switch). It leaves out the kernel changes an importer will actually hit.

**Fix:** rewrite it as the stable entry, drop "(draft)", and split it into these sections:
1. **Upgrading the npm package from 0.1.0:**
   - `getMethodAccess` changed from last-match-wins to a lattice join. This is an authorization change: holding more roles never grants less, and key order no longer matters.
   - Token caveats now deny access in `getMethodAccess`.
   - `RoleName` gains `configurator`.
   - `WriteOutcome.reason` gains `unattributed` and `immutable`, which breaks exhaustive switches.
   - `runWritePipeline` data now carries `_by`.
   - The schema validates content without the stamps, and `isUnchanged` ignores `_seq` and `_by`.
   - Say which `CollectionConfig` fields the kernel enforces (`requireAttribution`; `immutable` only when given a correct `exists`) and which only the endpoint handles (`seq`).
   - Note that 0.1.0 could not be imported under Node ESM.
2. **Upgrading a host from 0.1.0 or beta.1/beta.2:** a checklist covering error shape #20, the new codes, `immutable`, the `seq` guard, verified-email contact grants, the reserved `system` namespace, `unique` per field, and the slug derive `when: absent` change. Link to the beta.3 "Action required" audit.
3. **Security — affected versions** (plausible): for each fix, the first fixed version and the affected range. 0.1.0 hosts carry the unverified contact-email grant (`utilities.ts:258-289` at v0.1.0). Say plainly that the npm kernel itself was not affected.
4. **Repository:** a short section for OIDC publishing, the virta board and the production registry switch.

Also add a short "Upgrading from 0.1.0" note to the README, because it ships in the tarball and the CHANGELOG does not.

**Re-review:** docs lens over the new entry only.

## Majors (confirmed; fix before the tag)

### M1. Uniqueness has two implementations, and the batch path returns 500 (dryness, confirmed; correctness)
Files: `functions/src/docs.ts:328-339`, `functions/src/doc.ts:178`.
- **The two paths behave differently.** /doc's `isUnique` guards against values that are not a string or number and returns `400 unique`. The /docs batch closure has no guard.
- **A missing field gives 500 on the batch path.** If a batch body omits the unique field, `.where(f,'==',undefined)` throws inside the transaction and the endpoint returns `500 internal 'commit failed'`. The verifier confirmed the throw against the SDK.
- **Booleans and objects are handled differently.** /doc refuses them; /docs accepts them when nothing collides.
- **Status codes also differ.** A real collision is `400 unique` on /doc and `403 unique` on /docs.

virta writes through the batch path, and "unique per field" is one of this release's upgrade items.

**Fix:** use a single uniqueness primitive in both places, one form that runs with `.get()` and one with `tx.get()`, or at minimum copy the scalar guard into docs.ts. Add a test that sends a batch missing its unique field and expects `400 unique`. Fix this together with the minor status-map item below.

**Re-review:** correctness and blast-radius over the fix diff.
