## Blocker

**B1. The #23 fix covers new hosts only. Existing hosts, including virta's, keep live grants that anyone can claim, and the release notes don't say so.** *(blast-radius, confirmed)*. Files: `CHANGELOG.md`, `scripts/seed-production.js`, `scripts/sandbox-token.js`.
- Hosts seeded from the old `role.json` still grant owner, developer, admin, editor and author to `owner@gmail.com`, and admin to `admin@gmail.com`. `seed-production` only calls `.set()` and never removes these.
- Hosts where `sandbox-token --grant` ran still have `role/sandbox-<role>` keyed to `sandbox-<role>@example.test`. That account's password (`sandbox-test-password-not-a-secret`) is public, and #17 turned on email/password sign-in. The new code writes `sandbox-<role>-<run>` or `-pin` and never touches the old document.
- The uncommitted beta.3 CHANGELOG entry describes #23 but has no remediation step.
- **Fix:** add an **"Action required on existing hosts"** section. It should say to delete `role/owner-role`, `role/admin-role` and `role/writer-role` if they still have `@gmail.com` contacts or non-empty roles, every `role/sandbox-*` doc, and every Auth user matching `sandbox-*@example.test`. Better still, add a read-only audit command that lists these for an alias. Then run it against virta-7e070.
- Re-review: Tier 0 plus blast-radius over the notes and the script.

## Majors that must be fixed before tagging (confirmed, correctness/security)

**M1. Role resolution trusts an unverified email.** *(security + blast-radius, confirmed; merged)*. File: `functions/src/utilities.ts:305`.
- `findRoleDocs(uid, email)` falls back to matching `contacts` by email without checking `email_verified`.
- provision-sandbox step 4b enables password sign-in on every provisioned host, consumer hosts included. The API key is public.
- So anyone can `accounts:signUp` with an unclaimed contact email and get that document's roles: pre-assigned roles (a documented feature), clone-to-sandbox's `owner` document, and the old seed on any host where B1 hasn't been cleaned up. `.invalid` addresses can be registered too, so seed-safety.test's "cannot be registered by anyone" assertion claims more than it checks.
- The fallback itself predates this release, but #17 widened the exposure and virta's host is affected.
- **Fix:** take the email path only when `decoded.email_verified === true`. Add a unit test where an unverified token plus a matching contact resolves to anonymous. Reword the seed-safety test comment. Check that sandbox-token and verify-* still resolve through `userIds`.

**M2. The `system` namespace is not reserved.** *(security confirmed; correctness also flagged it, unverified; merged)*. File: `functions/src/collections/namespace.ts:124`.
- `validateManifest` accepts a manifest named `system` that declares `system:claim`, `system:host` or `system:registry` with public access. This was reproduced.
- `installed.ts` loads it, and `/doc` and `/docs` would then serve those paths.
- Three places assume these paths can't be reached: claim.ts:51, epoch.ts:19 and sandbox-lib.js:95.
- With one configurator-approved install, anyone could: mark a consumer host `platform-sandbox`, which turns off the new #23 probe guard; complete the claim ceremony and become configurator; or tamper with the epoch.
- **Fix:** reserve `system` (and any other internal prefix) in `refuseDeclaration`/`validateManifest`. Have `collectionsFor` refuse `system:*` regardless of what the registry contains. Add tests for both.

**M3. An immutable collection can be rewritten by DELETE followed by re-create.** *(security, confirmed)*. Files: `functions/src/collections/write-pipeline.ts:342`, `functions/src/doc.ts` DELETE branch.
- DELETE maps to the `write` grant. The DELETE branch never reads `config.immutable` and leaves no tombstone.
- A later POST to the same id passes the existence guard and gets a fresh `_seq`.
- On virta:event (immutable, seq, author `write: ALL`), any author can therefore re-order history. That is the exact thing #25 says it prevents.
- **Fix:** refuse DELETE on immutable collections unless the caller is privileged, or leave a tombstone. Add a test for delete followed by re-create. At the very least, stop the docs promising "order is not rewritten".

**M4. verify-token.js revokes the wrong role document.** *(correctness, confirmed)*. File: `scripts/verify-token.js:101`.
- `ROLE_DOC` is still hardcoded to `role/sandbox-agentboss`, but the grant now lives at `role/sandbox-agentboss-<run>`.
- A Firestore REST PATCH creates the document if it's missing. So the revoke step writes a stray document, "REVOKING THE HUMAN REVOKES THE AGENT" gives a false red, and cleanup leaves an orphan doc granting author+admin.
- This also makes the CHANGELOG's "cleanup keyed on the run" claim false.
- **Fix:** parse `SANDBOX_ROLE_DOC` from the `--export` output. Add `currentDocument.exists=true` to the revocation PATCHes. Do one live run against a marked sandbox.

Security and correctness:
- [ ] **Immutable PATCH works as a content oracle** *(security, confirmed minor)*, `functions/src/doc.ts:486`. For a principal with write but no read, 200 `unchanged` vs 409 `immutable` confirms guesses one field at a time, as many times as they like. Either reject PATCH on immutable collections (a log has nothing to merge), return the same response to non-readers, or document the disclosure. It doesn't affect anything in this repo; it affects consumers that configure write-without-read.
